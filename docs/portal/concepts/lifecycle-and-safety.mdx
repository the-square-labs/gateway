# Lifecycle and safety model

Gateway distinguishes a requested operation from its verified outcome.

## Desired state and observed state

The control plane stores desired configuration and operation state before dispatch. Daemons report observed runtime state. A successful API response may mean an operation was accepted; use Tasks, resource status, health, and events to confirm convergence.

## Reconciliation

Gateway retries safe idempotent work after transient disconnects and reconciles resources after application or daemon restart. It avoids inventing success from stale inventory. When ownership cannot be proven, mutations fail closed.

## Destructive actions

Deletion, credential rotation, migration cutover, archive import, database teardown, and certificate replacement have wider effects than ordinary edits. Read the confirmation text, check dependent resources, and verify the post-condition.

## Safe offline behavior

When a node is offline, Gateway may display a sanitized last-known snapshot. It does not allow a mutation that would rely on unverified current state. Existing services on the node may continue running independently.

## Long-running operations

Builds, migrations, deployments, certificate work, updates, and database provisioning are durable Tasks. Use operation history and logs rather than repeating an action because the page appears slow.
