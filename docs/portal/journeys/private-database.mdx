# Connect an application to a private database

This journey keeps the database unpublished and gives the application a binding-specific identity.

## Happy path

1. Enroll a dedicated database node.
2. Open **Databases** and create PostgreSQL, Redis, or ClickHouse from the supported catalog.
3. Keep **Publish TCP** disabled unless direct external access is a deliberate requirement.
4. Wait for provisioning and health checks to reach **Ready**.
5. Open the target Container, Deployment, or Compose service and create a managed database link.
6. Select the database and binding options.
7. Recreate or redeploy the workload when the UI indicates that environment/network material must be applied.
8. Test an application query and inspect binding runtime telemetry.

## Expected guarantees

- The workload does not receive the database owner credential.
- Every binding receives a distinct engine identity.
- Workload recreation preserves the binding.
- Binding deletion retires the binding identity without deleting the database.
- Database or Relay outages fail new admissions closed and recover through reconciliation.

## Do not

- Copy credentials from internal containers.
- Modify connector containers through user lifecycle APIs.
- Publish the database port merely to troubleshoot a private binding.
- Manually delete database roles unless the Gateway teardown runbook explicitly requires recovery.
